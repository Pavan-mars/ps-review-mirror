# CUBIC MARS Chicago — RDS schema and the S3 → Lambda → RDS → Dashboard map

05-Aug-2026. Generated by parsing the actual DDL in
`api/lambda/cubic-mars-dashboard-api/sql/*.sql` (49 files), every loader Lambda
under `api/lambda/`, and the API route handlers. Nothing here is from memory or
a design document — if it is in this file, it is in the code.

**Aurora PostgreSQL holds 178 tables and 85 views.**
Only **35 tables are written by a loader Lambda**. The rest are
derived through views, seeded by migration, or never populated.

---

## 1. The pipeline, as actually wired

```
  SageMaker / Databricks notebook
        |  writes CSV or parquet
        v
  S3   (TWO buckets — see 1.1)
        |  loader Lambda, VPC-attached, pg8000
        v
  Aurora PostgreSQL   (tables)
        |  CREATE OR REPLACE VIEW  — 85 views, this is the serving contract
        v
  cubic-mars-dashboard-api   (Lambda behind HTTP API Gateway)
        |  JSON
        v
  React dashboard   (ECS Fargate + nginx)
```

The **views are the contract, not the tables**. Every dashboard endpoint reads a
view, so a loader can change a table's shape without breaking the UI only while
the view still resolves — which is exactly why `CREATE OR REPLACE VIEW` failures
(`42P16`, cannot drop or retype a column) have been the recurring deploy break.

Three problems are visible in that table.

**PS1 has two loaders, on two different buckets, at two different prefixes.**
`ps1-rds-push` reads *gold* at `chicago/gold/device_ps1_cross_wired_daily`;
`ps1-xw-loader` reads *artifacts* at `chicago/device_ps1_cross_wired_daily`.
Same dataset name, different homes. One is almost certainly dead — and a dead
loader that still runs will overwrite live data with stale data. Resolve before
go-live, not after.

**PS2 and PS3-v2.5 write to un-partitioned bucket-root prefixes**
(`ps2_outputs`, `ps3_outputs`). Every other loader sits under `chicago/`.
Boston will collide there.

**Three loaders do not parameterise their prefix** (`ps3-v2-loader`,
`ps4-v3-loader`, `ps3-rds-push`), so the path is hard-coded in the body and
cannot be repointed by environment variable — which blocks a dev→UAT promotion
for the same reason the dashboard image did.

`ps4-rds-loader` reads from **both** buckets. That may be correct (clustering
artefacts vs scored output) but it should be stated, not inferred.
